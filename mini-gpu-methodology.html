Mini GPU Lite: methodology

One fixed-function triangle rasterizer, written once in SystemVerilog, deployed on two FPGA boards (Basys3 and ALINX Zynq-7020), verified bit for bit against a C++ model, and compared against CPUs. Two people: Member 1 builds and measures the hardware, Member 2 makes the 3D models in Blender. This page lists every stage, who owns it, what goes in, what comes out, and how we know it worked.

1. Research question

How does the same hardware rasterizer behave on two different FPGA platforms, and how does it compare with software on an embedded CPU and a desktop CPU, in speed, resources, energy, and data-transfer cost?

What we compare

#ComparisonSame thing kept fixedWhat changes
C1Basys3 vs Zynq-7020Identical gpu_core.sv, 100 MHz, 160×120Chip family, resources, host link (UART vs AXI)
C2Zynq FPGA fabric vs Zynq ARM Cortex-A9Same chip, same algorithm, same sceneHardware pipeline vs software loop
C3FPGA vs desktop CPUSame algorithm (golden model)Platform
C4Compute vs I/OSame sceneUpload / readback time vs drawing time

Expected result, stated up front: a 3+ GHz desktop core is faster than a 1-pixel-per-clock design at 100 MHz. The paper does not claim otherwise. The interesting results are C1, C2, energy per frame, and C4.

S1Define the data format (the contract) Member 1

Host and GPU talk only through these bytes, on both boards. Little-endian.

OpcodeCommandPayloadGPU reply
0x00PINGnone'G' 'P' 'U' 01
0x01CLEARcolor (2 B)A0 when done
0x02LOAD_TRI26 B trianglenone
0x03DRAWnoneD0 + cycles, tested, inside, written (4 B each)
0x04READnone19,200 pixels × 2 B
0x05RESET_TRISnoneA0

Triangle (26 bytes): x0 y0 x1 y1 x2 y2 (int16 each) · z0 depth at v0, dz/dx, dz/dy (int32, Q16.16) · color (uint16).

Files
pc/protocol.py, header of rtl/gpu_core.sv
Pass if
Python encoder, C++ parser and RTL parser agree (checked in S5).

S2Scene generation HOSTMember 1

  1. Model: built-in test scenes (cube, UV-sphere, random, grid, overlap) or a Blender model from S2b: center it and scale it to radius 1.
  2. Transform: rotate by the scene angle.
  3. Lighting: face normal n; brightness k = 0.25 + 0.75·max(0, n·L); color = base × k, rounded to RGB444.
  4. Projection: camera at z = −3, sx = W/2 + f·x/z, sy = H/2 − f·y/z, rounded to integer pixels.
  5. Depth: d = (1/z − 1/near)/(1/far − 1/near) scaled to 0…65535. This is linear in screen space, so a plane fits it exactly.
  6. Depth plane fit: from the 3 corners solve z = z0 + a(x−x0) + b(y−y0); send z0, a, b as Q16.16.
  7. Winding: order vertices so front faces have positive area. The FPGA culls the rest.
  8. Pack: RESET, CLEAR, LOAD_TRI…, DRAW, READ.
Command
python pc/make_scene.py cube · python pc/make_scene.py obj models/teapot.obj --angle 30 --tilt 15
Output
scenes/cube.bin (board), scenes/cube.hex (testbench), zynq/scene_cube.h (ARM)
Pass if
Golden image shows only camera-facing faces, lit from upper-left.

Steps for every model

  1. Model in Blender 4.x (or download a public-domain model and clean it). Keep the model's front facing −Y.
  2. Turn on the triangle counter: Viewport Overlays → Statistics.
  3. Reduce: add a Decimate modifier (Collapse), lower Ratio until Triangles ≤ 1024. Try Planar for hard-surface models.
  4. Clean: Edit Mode → select all → Mesh → Clean Up → Merge by Distance; then Mesh → Normals → Recalculate Outside.
  5. Color: one material per color, set Base Color only. Use strong, different colors (the GPU has 16 levels per channel).
  6. Apply modifiers and the object's scale/rotation (Ctrl+A → All Transforms).
  7. Export: File → Export → Wavefront (.obj). Settings: Selection Only on; Forward −Z, Up Y (defaults); Geometry: Apply Modifiers on, Triangulated Mesh on; Materials: Export on (writes the .mtl). UVs and normals can stay on; they are ignored.
  8. Check: python pc/check_models.py models/teapot.obj --angles 0 45 90. It must say OK; open results/preview_teapot_a0.png etc.
  9. Reference image: in Blender, Front view, Viewport Shading → Solid, Lighting Flat, Color Material; screenshot. Save as models/ref_teapot.png for the side-by-side figure.
  10. Log it in models/MODELS.md: name, source/license, triangle count, materials, notes.
Output
models/*.obj, *.mtl, ref_*.png, MODELS.md, results/models_report.csv
Pass if
check_models.py OK for all; previews show the model's front, right colors, filling a good part of the screen; no missing faces.

S3Golden model (the reference truth) Member 1

A C++ program that does exactly the integer steps the hardware does, in the same order. It defines "correct".

Algorithm

edge e(a→b, p) = (px−ax)(by−ay) − (py−ay)(bx−ax)
e0 = e(v1→v2)   e1 = e(v2→v0)   e2 = e(v0→v1)
area = e2 at p = v2          → if area ≤ 0: cull (back face / flat)
box  = min/max of x, y, clamped to the screen → if empty: cull

top-left fill rule: bias = 0 on top or left edges, else 1
start at box corner: E_i = e_i(minx, miny) − bias_i
                     z   = z0 + dzdx(minx−x0) + dzdy(miny−y0)

for each row:   for each pixel:
    inside = E0 ≥ 0 and E1 ≥ 0 and E2 ≥ 0
    if inside and depth16(z) < zbuf[p]: write depth + color
    step right:  E_i += A_i (= by−ay),  z += dzdx
  step down:     E_i += B_i (= ax−bx),  z += dzdy

Cycle model (predicts the hardware exactly)

cycles = 3 + Σ over triangles ( 5           if culled
                                6 + box_w × box_h   if drawn )
Command
golden scenes/cube.bin results/cube
Output
results/cube_golden.bin (frame), cube_golden.json (counters, CRC32, predicted cycles, CPU ms/frame)
Pass if
Grid scene: inside = 19,200 exactly (every pixel covered once: fill rule works).

S4RTL design FPGA Member 1

ModuleJob
uart_rx.sv / uart_tx.svSerial ↔ bytes, 921600 baud (Basys3 only)
gpu_core.svCommand FSM, triangle BRAM, counters, reply and readback
rasterizer.svSetup + walk, 1 pixel per clock
depth_unit.sv2-stage Z-test, depth + color BRAM, clear engine
sdp_ram.svSimple dual-port BRAM template
basys3_top.svBoard wrapper: UART + LEDs
zynq/gpu_axil.vAXI-Lite wrapper for the ARM (TX, STATUS, RX, ID registers)

Rasterizer state machine

IDLE → FETCH → LATCH → SETUP1 → SETUP2 ─(culled)→ NEXT
                                  └→ SETUP3 → WALK ×(box pixels) → NEXT → FETCH … → DONE
SETUP1: A, B, bias, area, box      SETUP2: cull test, multiplies (registered for timing)
SETUP3: start values               WALK:   test + emit fragment, then add A or B

Depth hazard

The depth unit reads at cycle t and writes at t+1, so a new fragment at the same address one cycle later would read stale depth. Inside one triangle all addresses differ. Between triangles the setup takes at least 6 cycles, which is longer than the 2-cycle window. So no stall or forwarding is needed in this version.

Pass if
Verilator -Wall lint clean; Vivado timing met at 100 MHz (WNS ≥ 0).

S6Basys3 deployment Member 1

  1. Build: vivado -mode batch -source vivado\build_basys3.tcl
  2. Check results\basys3_board_timing.rpt: WNS must be ≥ 0.
  3. Program: vivado -mode batch -source vivado\program_basys3.tcl. LED0 should blink.
  4. Run: python pc\run_board.py cube --port COM5 --draws 10
  5. Compare: python pc\compare.py cube results\cube_basys3.bin --tag basys3 --timing results\cube_basys3_timing.json
  6. Repeat for all 5 scenes.
Output
Board frame PNG, diff PNG, json with cycles + upload/readback seconds
Pass if
Same criteria as S5, on real hardware. Board cycles equal simulation cycles.

S7Zynq deployment Member 1

  1. Vivado project with the Zynq part; add gpu_axil.v + the 4 core files.
  2. Block design: ZYNQ7 PS (ALINX preset) → Add Module gpu_axil → Connection Automation → FCLK_CLK0 = 100 MHz.
  3. Note the base address, generate bitstream, export hardware (.xsa).
  4. Vitis: platform from .xsa, app with zynq/main.c + scene_cube.h.
  5. Run; terminal at 115200 prints FPGA cycles, CRC, link times, and the ARM software time for the same scene.
  6. For a full image check: DUMP_FRAME 1 → save log → pc\zynq_log.py → compare.py --tag zynq.
Pass if
FPGA CRC = ARM CRC = golden CRC.
Fallback
If the board fails: vivado\core_compare.tcl still gives Zynq resources, timing, power ("implementation only").

5. Limits (state them in the paper)

  • Transform, projection and lighting run on the host, not the FPGA.
  • Flat color per triangle; no texture, no Gouraud.
  • No near-plane clipping; scenes keep the camera outside the model.
  • Integer vertex positions (no sub-pixel precision). Faces seen almost edge-on (about 1–5 pixels) can be culled or kept against the true 3D facing because of this rounding.
  • Models must stay under 1024 triangles; textures and smooth shading from Blender are ignored.
  • Power numbers are Vivado estimates unless measured on the board.
  • One pixel per clock; a multi-pixel version is future work.

User runs run_board.py cube --port COM5
→ scenes/cube.bin (made by make_scene.py; the bytes to send)
→ pc/run_board.py (sends commands, waits for replies, times them; passes bytes over USB-UART)
→ rtl/uart_rx.sv (bits → bytes; passes 1 byte per pulse)
→ rtl/gpu_core.sv (decodes, stores triangles, starts DRAW; passes 208-bit triangle words)
→ rtl/rasterizer.sv (setup + walk, 1 pixel/clock; passes fragments: address, depth, color)
→ rtl/depth_unit.sv (Z-test, writes BRAM; passes frame on READ)
→ rtl/uart_tx.sv (bytes → bits back to the PC)
→ results/cube_basys3.bin + cube_basys3_timing.json
→ pc/compare.py (vs golden; writes PNGs + json) → PASS / FAIL

Zynq run

zynq/main.c (ARM pushes the same bytes from scene_cube.h)
→ zynq/gpu_axil.v (TX / STATUS / RX registers)
→ gpu_core.sv → rasterizer.sv → depth_unit.sv (same as Basys3)
→ main.c (prints cycles, CRC, link times, then the ARM software time + CRC)
→ pc/zynq_log.py → pc/compare.py --tag zynq
